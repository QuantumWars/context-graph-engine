The five algorithms

A context graph engine for agentic systems: what an agent knew, decided and derived, on a record that can prove it has not been altered — and can still forget something on request.

Status. Stages 1 and 2 complete. All five are pure functions over plain data — no I/O, no store, no framework — with 153 tests, every guard seen red against a named source change before it was claimed. the store, the retrieval path and the CLI are wired on top of them in Phase 2 without any of the five changing.

Provenance. Each algorithm is a port from semantica-agi/semantica v0.6.5, studied read-only, followed by a research step and a recorded decision. Where we diverge, the reason is stated and the original's reasoning is carried over rather than discarded — four things in that repository are genuinely good and are taken close to verbatim.

Why this exists

An agent accumulates history. A transcript is a poor way to hold it, because a transcript answers none of the questions that actually get asked:

  • What did we know at time T? — and coherently, not a filtered list with edges pointing at things that are not there.
  • Why was this decided? — the chain of causes, and how much of it to trust.
  • What precedent applies here? — across more than one way of searching.
  • Has this record been altered? — because a memory you cannot audit is a liability rather than an asset.

And one that only shows up later, at the worst possible time: can we delete something we should never have stored? An agent reads a tool result containing a live API key and records it. That key is now in your history. The whole of Algorithm 3 exists for that moment.

The shape of the store

One append-only file. Every derived view — node table, adjacency index, decision lookup, lexical index — is rebuilt on load and never written to disk.

<workspace>/.claude/graph-engine/
  log.jsonl      the only source of truth, one JSON object per line
  .gitignore     excludes the whole directory, written when it is created
A persisted derived copy would be a second store, and a second store for one fact is the defect that motivated most of this design — see the box below.
The defect this whole design is shaped around

Semantica writes a decision twice: once as a graph node, once as a plain dictionary. An AST query over the real class shows which methods touch the dictionary:

save_to_file                 False      record_decision              True
load_from_file               False      find_precedents_by_scenario  True
purge_node                   False
clear                        False

Written by one pair of methods, read by neither the persistence pair nor the erasure pair. So saving and reloading silently loses precedent search, and a purged decision stays searchable by its full text. One log with rebuilt views makes that class of bug structurally impossible rather than merely avoided.

1 · The hash-chained record design changed by research

Make tampering visible, without making forgetting impossible.

src/provenance/chain.ts · src/provenance/canonical.ts · ported from semantica/provenance/integrity.py and manager.py:1415-1485

First, the bytes: canonical form

You cannot hash a record until you agree exactly which bytes represent it. JSON is not deterministic — key order, number formatting and whitespace all vary between serialisers, languages and runtime versions. Hash a record on two code paths and you get two digests, and the difference reads as tampering. A false accusation is worse than no check.

So every digest goes through one function, implementing the rule standardised as RFC 8785, the JSON Canonicalization Scheme:

  • Object keys sorted ascending by UTF-16 code unit — not by locale.
  • No insignificant whitespace anywhere.
  • null written explicitly; an absent key omitted entirely, so omission and null stay distinct and must survive a reload unchanged.
  • NaN and Infinity are errors, not coercions. JSON.stringify silently turns both into null, which would make two different records hash identically.
What this replaces

The original concatenates sixteen field values with no separator at all:

data = (f"{entry.entity_type}"
        f"{entry.activity_id}"
        f"{entry.agent_id}" ... )     # 16 fields, glued

So the field pair ("ab", "c") and the pair ("a", "bc") produce an identical digest. A separator does not fix this — any separator can occur inside a value. JSON is self-delimiting, which is the actual fix.

The commitment — and why it is not just hash(content)

The obvious design hashes the record's content directly. It is also the design that makes deletion impossible, and we had already committed that deletion must work.

THE TRAP

  digest(N) = hash( content(N) + digest(N-1) )

  Delete content(N)  →  digest(N) no longer matches
                     →  record N+1 points at a fingerprint that does not exist
                     →  the chain is broken

  ...which is EXACTLY what an attacker deleting a record looks like.
  The chain cannot tell "the owner asked us to forget" from "someone tampered".
Neither system we studied solves this. Semantica scopes purge to a separate subsystem its chain does not cover. memory/src/facts.ts never erases at all — "nothing is deleted, only invalidated".

The answer from the cryptographic-erasure literature is neither of those: keep the payload out of the hashed material and commit to it instead.

contentDigest = SHA-256( salt ‖ canonicalJson(content) )        ← the commitment
digest        = SHA-256( canonicalJson(record − digest − content − salt) )

              contentDigest  IS INSIDE  digest
              content, salt  ARE NOT
The chain attests to the commitment, never to the payload. So the payload can be removed without touching anything the chain depends on.
The consequence

A purge sets content = null and salt = null. It leaves digest, prev, seq and contentDigest untouched — so the chain still verifies, before and after the purged record, with no gap and no break.

Why deleting the salt is the load-bearing half

Without a salt, contentDigest is just hash(content). If the content had low entropy — a boolean, a status flag, a short name — an attacker holding the surviving digest hashes every candidate until one matches, and the "erased" content is recovered.

With a per-record random salt deleted alongside the content, they must guess the content and a random salt at once. That is not feasible. A purge that kept the salt would be theatre.

The two are therefore removed together, always. Removing one but not the other is not a partial purge — it is a corrupt record, and the verifier says so.

The salt is also length-prefixed rather than merely concatenated, so the salt/content boundary cannot be slid — the same ambiguity the canonical form closes inside the content:

sha256(`${salt.length}:${salt}${canonicalJson(content)}`)

Verification: four checks, in order

Splitting the payload out of the chain link means the payload needs a check of its own — otherwise editing content in place would no longer be caught by anything.

#CheckReason codeSkipped when
1contentDigest re-computes from salt ‖ contentcontent_tamperedthe record is purged
2digest re-computes from the record's other fieldsdigest_mismatchnever
3prev equals the predecessor's stored digestchain_breaknever
4seq equals predecessor's seq + 1sequence_gapnever
A purge must not become a way to hide tampering

A purged record skips only check 1. It still faces 2, 3 and 4. If a purge exempted a record from the chain checks, then "purge" would be an attacker's tool, and the erasure feature would have destroyed the integrity feature it was meant to coexist with. There is a test named exactly that, and the demo shows it firing.

Why check 3 and check 4 both exist

They look redundant and are not. Two distinct records could, in principle, share a digest — and a link-only check would then miss a gap that the sequence check still catches. Deleting a record trips both signals on its successor, which is much harder to forge than either alone. The original states this reasoning at the site, and it is carried over.

One corrupt record must not cascade

After examining each record, the verifier advances its expectations from that record's own stored fields — whether or not it was just flagged.

expectedPrev = e.digest;   // not "what we thought it should be"
expectedSeq  = e.seq;

Without this, one tampered record in the middle makes every record after it look broken too, and the report tells you nothing about where the problem actually is.

Carried over unchanged, because the original is right

Link before hashing. prev is assigned then the digest is computed, so the link sits inside the digest. A link stored beside the digest could be rewritten without detection.

One place we deliberately diverge

Semantica excludes its primary key from the hash, and explains why: its versioning archives a prior value under a new id, so hashing the id would turn a legitimate rename into a permanent false chain break. It also records what that costs — a row whose id is swapped while its content is kept is no longer caught.

We hash every field except digest, content and salt, with no id exclusion, because we do not inherit the cause: records here are immutable and a correction is a new record, so no id is ever relabelled.

Why a flat chain and not a Merkle tree

Crosby & Wallach's history tree (SIGIR 2009, adopted by Certificate Transparency) turns linear verification into logarithmic proofs. Its advantage is proving something to a party that does not hold the log. We have no such party — one local principal, no network surface, no remote verifier — and verification here is a full scan by the process that already holds everything, where a chain and a tree cost the same.

The trigger to change is named: the first time something that does not hold the log must be convinced of its consistency. Note that a Merkle tree has the same deletion problem — the commitment design above is what solves it in either structure.

2 · Bitemporal windows and stateAt

What was true then — and, separately, what we believed then.

src/temporal/window.ts · ported from semantica/context/context_graph.py:2590-2631

Two time axes, and why one is not enough

SQL:2011 separates two independent dimensions, and gives each its own table type:

AxisMeansSupplied byField
Valid timethe period a fact correctly reflects realitythe callervalidFrom / validUntil
Transaction timethe period the store held the recordthe enginerecordedAt

Bitemporal means both. Semantica's comments describe its windows as bitemporal, but it carries only valid time — so the question "what did the store believe in March?" has no answer there.

Why the second axis matters here specifically

A decision made in March, on the information available in March, is not wrong because April corrected the record. A snapshot that silently applies April's knowledge to a March decision misrepresents every past decision it explains. Precedent retrieval has the same shape: the precedent that should have been found is the one that existed at the time.

And it was nearly free. Algorithm 1's append-only log already orders records by insertion, so recordedAt is transaction time and asOf is a truncation of the input. No second store, no history table, no versioning scheme — the structure built for tamper evidence carries the second axis as a side effect.

stateAt(nodes, edges, { validAt, asOf })

  1. TRANSACTION TIME   drop everything recorded after `asOf`
  2. VALID TIME         keep records whose window contains `validAt`
  3. ENDPOINT RULE      keep an edge only if BOTH endpoints survived step 2
The order is not cosmetic. Reversed, a record written in June could influence a snapshot of what was believed in March.

The endpoint rule

An edge is admitted only when its own window is open and both of its endpoints are active. This is the single rule that makes a snapshot a coherent view of something rather than a filtered list — without it, a snapshot can contain an edge pointing at a node that is not in the snapshot.

The test asserts it computed from the result, not against a hardcoded expectation, so a new way to leak a dangling edge fails without anyone remembering to add a case:

const ids = new Set(snapshot.nodes.map(n => n.id));
expect(snapshot.edges.length).toBeGreaterThan(0);   // anti-vacuity first
for (const e of snapshot.edges) {
  expect(ids.has(e.source)).toBe(true);
  expect(ids.has(e.target)).toBe(true);
}

Malformed input fails closed, not open

Semantica

An unparseable bound parses to None, and is_active then imposes no bound at all, logging "treating node as Always-Active".

A corrupted timestamp makes a record more visible, and a record that should have expired never does.

Here

An unusable bound excludes the record and appends a reason code to rejected. Excluded and named — an invisible record with no stated reason is its own bug.

Two tightenings follow from the same rule:

  • A date-time with no offset is rejected as ambiguous_timezone rather than assumed to be UTC. If the value was local, the record silently moves by hours — a wrong answer wearing the shape of a right one. A date-only value is still accepted as UTC midnight, because that is a stated convention rather than a guess.
  • An inverted window — start after end — is reported. Such a record can never be active, so it is a defect in whatever wrote it, not an intent to hide something.

3 · Retract and purge two operations, two record types

"This is no longer true" is a completely different statement from "this should never have been captured".

src/temporal/retract.ts · ported from semantica/context/context_graph.py:1556-1919

RETRACT

Closes the validity window and files a retraction record. The content stays. History still answers "what was the policy in March?"

For: a superseded policy, a fact that stopped being true, a decision that was reversed.

PURGE

Removes the content and leaves a tombstone that deliberately holds none of it. The record is gone; only the fact that something was here remains.

For: a leaked credential, personal data, anything that should never have entered the store.

The narrowing rule

A retraction takes the earlier of an existing end bound and the retraction instant. It can only ever narrow a window, never widen one.

closingValidUntil(current, at) = min(current, at)      // roughly
What breaks without it

A record whose window already closed in February, retracted in June, would be reported active for the four months in between — because the retraction "set" its end bound to June. The original states this reasoning in the function's own docstring, and it is carried over.

An untrusted existing bound closes at the retraction instant. That is the safe direction, and it stays consistent with the fail-closed rule: an untrusted bound results in less visibility, never more.

The tombstone holds nothing

{ type: 'tombstone', id, kind, purgedAt, reason,
  contentDigest,                 // kept: proves something was committed here
  scope: 'this-store-only' }     // the honest scope statement

The test is written the way the requirement was written — it scans the serialised tombstone for every field value of the purged content, not a sample, so a content field added later is caught without anyone remembering. And it proves the scan can find a value when one is present, so a pass means "absent" rather than "the scan is broken".

Why every tombstone states its scope

GDPR Art. 17 reaches every copy of the data, and a controller must take reasonable steps to inform other holders, who then become independently responsible.

This store can clear its own copy. It cannot reach a copy something else made — a backup, an export, another machine that synced. Semantica's own docstring calls purge "one step of an erasure workflow, not the whole of it", and the research says that posture is correct rather than a cop-out. So it is carried over and made machine-visible instead of left in prose.

A tombstone without it would imply an obligation had been discharged when only part of it had — and the party most likely to be misled is a future session of this engine, telling a user their data "has been erased".

Cascade, and a subtle bug worth inheriting the fix for

Retracting a node closes every edge incident to it. The set of already-retracted edges is snapshotted before the loop, never consulted live.

Why that ordering matters

Semantica's edge ids are content-derived and can collide, so two distinct edge objects may share one id. With a live set, the record written for the first blocks the second from ever being closed — leaving an edge open against a retracted node.

Our first test for this used two edges with distinct ids and therefore could not have caught the bug at all. It was rewritten around two edges sharing an id, and only then did reintroducing the bug turn it red.

4 · Reciprocal Rank Fusion

Combining two searches without pretending their scores are comparable.

src/retrieval/rrf.ts · ported from semantica/vector_store/hybrid_search.py:148-186 · Cormack, Clarke & Buettcher, SIGIR 2009

score(d) = Σ  1 / (k + rank_c(d))          k = 60, ranks 1-based
           c

summed across every channel c that returned d. Nothing normalised.

The channels here are lexical and structural. Their scores are not on a common scale and never will be — a keyword score and a graph-connectivity score measure different things — so any scheme that adds their magnitudes is adding units that do not compare. RRF uses only the rank, which every channel produces in the same units by construction.

What it replaces, and why that is a defect and not just crude

Semantica's context retriever min–max normalises each source independently before weighting. Concretely, with one channel that found nothing useful and one that found something excellent:

lexical      junk-a=0.02   junk-b=0.01        ← found nothing useful
structural   excellent=0.98  ok=0.40          ← found something excellent

PER-SOURCE MIN–MAX                        RECIPROCAL RANK FUSION
  junk-a      1.000  ← promoted!            excellent   0.01639
  excellent   1.000  ← tied with junk         junk-a    0.01639
  junk-b      0.000                           ok        0.01613
  ok          0.000                           junk-b    0.01613
Min–max makes the best result within a source 1.0 whether it is excellent or the least-bad of three irrelevant ones. A source that found nothing still contributes a maximally-scored candidate, and no downstream weight can recover the lost signal.
How the test proves this rather than asserting it

The rejected algorithm is implemented in the test file. The test first proves min–max really does tie junk with excellent on that exact input, and only then checks that ours does not. A pass therefore means "we fixed a real defect", not "the fixture was toothless".

Three defects in the original, fixed

OriginalConsequenceHere
result.get("id", str(id(result)))a result with no id silently becomes its own key and can never fuse across channelshard error, missing_id, naming the channel and position
reconstruction is last-list-winsthe payload kept is whichever channel happened to come lastevery channel's contribution is kept
result["score"] = scorethe per-channel score is overwritten by the fused one, destroying the evidence for the rankingthe original score is retained per channel

Every result can explain itself

{ id: 'b', fusedScore: 0.03252,
  contributions: [
    { channel: 'lexical',    rank: 2, score: 3.1, rrf: 0.01613 },
    { channel: 'structural', rank: 1, score: 0.9, rrf: 0.01639 },
  ] }

A ranking that cannot be explained cannot be debugged, and a retrieval system nobody can debug gets turned off.

What k = 60 actually buys

It damps the dominance of a single high rank, so an outstanding vote from one channel becomes comparable to agreement across channels rather than overwhelming it. A candidate ranked 2nd by both channels can beat one ranked 1st by only one — which is usually what you want, and is the paper's central result.

5 · Decision nodes and causal chains

Why something was decided, and how much of that chain to believe.

src/decision/causal.ts · ported from semantica/context/context_graph.py:2734-2772 and :3938-3974

A decision is a node. That is the only copy.

This is the whole of the defect in the box at the top. There is no shadow dictionary, no separate decision index, nothing that a save could miss or a purge could fail to reach. decisionContent() reads from the node, and there is nowhere else to look.

Three edge types, and the distinction they encode

CAUSED  ·  INFLUENCED  ·  PRECEDENT_FOR

These are what a caller asserted — as distinct from relationships a heuristic inferred from shared entities and timestamps. Only asserted edges are traversed. Mixing the two would let a guess masquerade as a record, and the original is careful about this at its definition site.

The casing trap, fixed at the boundary

In Semantica, record_decision writes node_type="decision" while add_decision writes "Decision". Two readers compare with .lower(); two compare exactly. So decisions created one way are invisible to two of the four readers.

Here there is one canonical form, normalised once at the boundary, and no reader compares a raw string anywhere.

Per-path cycle detection, not a global visited set

        incident
        ├── postmortem ── add-gate ──(0.3)── slow-ci
        └── hire-sre ──────────────(0.2)──── slow-ci

  GLOBAL visited set:   finds one route, silently drops the other
  PER-PATH:             finds both
A node already on the current path is not revisited — but a node reached by one branch may still be reached by another. Semantica's own comment says a global set "silently loses valid chains", and a diamond is the smallest case where that bites.

Two confidence numbers, deliberately never blended

FormulaAssumesRead as
productConfidencew₁ · w₂ · … · wₙhops are independent — along a causal chain they usually are nota lower bound
weakestConfidencemin(w₁ … wₙ)nothingthe weakest link

The product can never exceed the minimum, so reporting both brackets the answer. The report also names which hop is the weakest, so a reader can see where the chain is thin rather than only that it is.

Why we refuse to emit a single number

The hop weights themselves are uncalibrated — nothing in this engine has measured what a weight of 0.7 means. Collapsing uncalibrated inputs through either operator produces a figure with more apparent precision than its inputs carry.

Noisy-OR was considered and is the wrong operator here, by its own definition: it combines several independent causes of one effect — parallel evidence — not serial composition along a path. It would be right for a question this engine does not yet ask: several distinct chains supporting the same decision.

What was deliberately not ported

The original ends by turning the product into an English verdict — "high confidence", "is weak evidence" — using thresholds of 0.7 and 0.4. Those constants are not derived from anything, and could not be: semantica/evals/__init__.py is ten lines reading __status__ = "coming_soon", so no threshold in that system has ever been measured.

A prose verdict built on unmeasured thresholds is more dangerous than the raw number, because it reads as a conclusion. Dropped.

One more fix: a stored weight of 0.0 means "this link carries no confidence", which is the opposite of the 1.0 default it could be mistaken for. The original reads float(hop.get("edge_weight", 1.0)); we read the weight directly, and there is a test pinning it.

Wired together — the store phase 2

Five pure algorithms, one append-only file, and nothing derived on disk.

Stage 1 built the algorithms as islands: no I/O, no store, no imports between them beyond a shared type. Stage 2 added callers. None of the five changed to make that work, which was the point of keeping them pure — if an algorithm had needed to change to be wired, that would have been a finding about Stage 1 rather than something to patch quietly.

engine record ──┐
engine link   ──┤
engine retract──┼──► Store ──► appendEntry (1) ──► log.jsonl   ← the only file
engine purge  ──┘       │
                        ├──► stateAt (2) ──────► point-in-time snapshot
                        ├──► closingValidUntil (3) at READ time
                        ├──► findChains + chainReport (5) ────► why
                        └──► lexical + structural ──► fuse (4) ─► retrieval decision
Every mutation goes through one build path, so nothing can write a record that skips the chain. Node table, adjacency and decision lookup are rebuilt on load and never persisted.
A bug the tests caught in this design, worth showing

The first retract closed a window by editing the record and recomputing its digest. That is exactly what DEC-007 forbids — records are immutable, corrections append — and the consequence was immediate: every later record's prev still pointed at the old digest, so one retraction broke the whole chain.

StoreError: chain_invalid: … first is chain_break at seq 2

Nothing in the code stopped it. The types were satisfied and the algorithm was right in isolation; only an integration test over a real file caught it. The fix: derive the closure at read time by folding the narrowing rule over every retraction. The log stays append-only.

What happens when a neighbour fails

The Stage 2 question is not "what does A call" but "what happens when B is absent, slow or wrong". Every connection has an answer and a reason code — 23 of them, each verified to exist in the source. A selection:

Uncalibrated constants, declared

Every number below ships as a declared placeholder, annotated at its definition site. None has been measured against this engine's own data, because there is no evaluation harness yet — and building one is the single most load-bearing gap in the project.

This is the discipline the studied system lacked. It ships 28 ingest connectors, 10 storage backends and 89 CLI commands, and an evaluation package of ten lines reading "coming_soon" — so every weight and threshold in it is uncalibrated by construction, and nothing in the repository could establish otherwise. Breadth was funded ahead of the instrument that would say whether any of it works.

Why a demo as well as tests

A test asserts what its author expected. Watching the thing run shows what actually happens. Those are different kinds of evidence, and the second one catches assumptions the first one bakes in.
